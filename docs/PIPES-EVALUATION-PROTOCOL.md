# ETH3D pipes: first measured-reference protocol

This is a **small fixed-camera research experiment**, frozen before looking at reconstruction-to-laser errors. Its purpose is to test whether image-derived sparse and depth points land near a measured rigid scene. It is not an ETH3D leaderboard result or a turntable-object accuracy claim. The input and acquisition record are in [RIGID-REFERENCE-PLAN.md](RIGID-REFERENCE-PLAN.md).

## Source conventions that govern the experiment

ETH3D's [multi-view format documentation](https://www.eth3d.net/documentation) defines the undistorted DSLR images as matching `PINHOLE` cameras and `images.txt` poses; the pose maps world coordinates into each camera. For a point `X_world`, calculate `X_cam = R X_world + t`, require `z_cam > 0`, then project with `u = fx*x_cam/z_cam + cx`, `v = fy*y_cam/z_cam + cy`. The documented pixel origin is the **top-left corner** of the image, not the first pixel's center. Convert an image pose to camera center with `C = -R^T t`. Scale `fx, fy, cx, cy` by the exact image resize factors; leave `R,t` and the scene length unit unchanged. Parse and validate quaternion normalization and rotation direction with forward/back projection before reconstructing.

The `scan1.ply` points are in scan-local coordinates. The `MLMatrix44` attached to that scan in `scan_alignment.mlp` maps them **from scan coordinates into the global camera-world frame**; apply it once, by the matching mesh filename, with homogeneous coordinates. ETH3D documents this transform and calls the `eval` cloud the cleaned version with points assumed to be visible in at least two images. That condition concerns the original scene's full image set, not necessarily the four views used here. `points3D.txt` contains SfM triangulations, not measured surface truth. [Format and scan definitions](https://www.eth3d.net/documentation).

Use metres for scan/world distances. This follows the [official evaluator's](https://github.com/ETH3D/multi-view-evaluation) metre-labelled laser beam parameter and its example tolerances `0.01,0.02,0.05` for the site's [1, 2 and 5 cm thresholds](https://www.eth3d.net/high_res_multi_view). Verify that the parsed camera baselines and transformed scene extents are physically plausible; do not silently rescale either cloud to improve agreement. Published camera calibration was refined against the scans, so agreement in that frame is measured-surface consistency conditional on the supplied calibration, not an independent camera-pose validation. [Benchmark paper, §§3.2 and 4](https://www.eth3d.net/data/schoeps2017cvpr.pdf).

## Freeze before reconstruction or error inspection

1. Validate all **14** image files against their `images.txt` names, image dimensions against their `cameras.txt` entries, finite positive `PINHOLE` intrinsics, unique IDs, finite rigid world-to-camera transforms, the PLY header/count, and the MLP matrix. Keep a complete 14-view metadata manifest with file hashes. This metadata is available for audit, but only the selected images enter the first reconstruction.
2. The first four input views are fixed by lexicographic filename: `DSC_0634.JPG`, `DSC_0635.JPG`, `DSC_0636.JPG`, `DSC_0637.JPG` under `pipes/images/dslr_images_undistorted/`. Record their camera IDs, ordered pairs and hashes in the run manifest. Check image overlap from the images and camera geometry and report if it is inadequate; do not swap images after seeing laser distances. The other ten remain out of reconstruction and can later test generalization; no held-out result is implied in this first run.
3. Resize those four undistorted images once, preserving aspect ratio with longest side at most **1024 pixels**. Record final width/height and per-axis intrinsic scale factors. Keep the full-frame pixels; any manually chosen image-only crop or mask must be fixed and hashed before comparing with the scan. Use supplied poses and intrinsics unchanged apart from resizing. Record CPU model, thread count, memory cap or measured peak RSS, program revision and all matcher/depth/fusion parameters before the run. No new model fitting or parameter choice from laser errors.
4. Produce an unfilled sparse point cloud first. The frozen CPU baseline uses OpenCV SIFT (at most 4096 features per image), strict mutual matches with a 0.8 ratio gate and at most 2-pixel square-root Sampson error under the supplied fixed poses. Tracks use full conflict components; accepted ray-intersection points require positive depth in every support view, at least 1 degree acute parallax, at most 4-pixel reprojection error and a conditioning limit of `1e8`. If the existing CPU depth path subsequently supports these views, produce an unfilled depth/fusion point cloud as a **separate stage** with its own frozen parameters. Both stages use image measurements only: the eval scan, MLP, scan renderings/depth, and `points3D.txt` cannot provide seeds, depth bounds, masks, camera refinements, fusion support, or acceptance gates. Preserve invalid/missing depth as missing. Record attempted and accepted matches, reconstructed counts, support views, rejection reasons, wall time and peak RSS; an empty cloud is a failure, not a missing score.
5. Seal the output cloud(s), stage manifest and hashes before reading laser distances. Keep any later method revision as a new run with its own parameters and output; never overwrite this baseline. Apply the scan alignment only in the evaluator. Do not estimate an ICP, similarity transform, scale or per-point registration against the laser cloud.

## First-run score: explicitly descriptive

For the first frozen sparse output `R` and transformed laser cloud `S`, calculate **one-way** exact Euclidean nearest-neighbor distances from every accepted sparse point to the laser cloud in the common frame. Set thresholds **0.01, 0.02, 0.05 and 0.10 m** before seeing results. Report the denominator, counts, fractions, median, p90, p95 and maximum, including every miss; an empty output is a failed reconstruction. See [PIPES-SCORE.md](PIPES-SCORE.md) for the scorer contract. This first execution reports no reverse or completeness readout.

The following broader readouts are reserved for a later, separately frozen evaluation and are **not** part of the first execution:

| Readout | Denominator and calculation | Interpretation |
| --- | --- | --- |
| Reconstruction-to-scan proximity | Every accepted point in `R`; count `d(r,S) <= t` and report median/p90/p95/max of `d(r,S)`, including misses. This is the only first-run readout. | Distance to available measured surface. A distant point can lie in unscanned space; this is **not official accuracy**. |
| Projectable scan-to-reconstruction proximity | Fixed subset `S4` of eval points projecting with positive depth inside at least **two** of the four selected full-resolution camera images; count `d(s,R) <= t` over every `s` in `S4`, and report median/p90/p95, including misses. | A four-view scope diagnostic. Projection does not prove unoccluded visibility, so this is **not completeness**. |
| Support/coverage | Report `|R|`, `|S|`, `|S4|`, `|S4|/|S|`, fraction of selected image pixels with valid output depth where depth was attempted, and per-view support counts. | Shows how much output and reference each fraction represents; no filled pixels count as observed. |

If a later study uses `S4`, calculate it once from the supplied cameras and eval points before opening output cloud distances, and hash its point indices. The projection test must use the original full-size calibration; using resized cameras is equivalent only if image bounds and scaling are handled exactly. A scan point projected into two images can be hidden behind a foreground surface in either or both. The laser cloud itself also has gaps. Consequently, a missing reconstruction near such a point is a useful diagnostic but cannot be counted as a proven four-view failure. Conversely, proximity to a scan point alone cannot establish that a reconstructed point is on the correct visible surface. Label the first-run numbers **local one-way proximity diagnostics**. Do not compute an F1 score or compare these percentages to ETH3D's published scores.

ETH3D's [paper](https://www.eth3d.net/data/schoeps2017cvpr.pdf) defines official completeness on the reference points, but treats accuracy through scanner beam free-space versus unobserved-space classification and voxel-normalized averaging. Its [evaluator README](https://github.com/ETH3D/multi-view-evaluation) lists `reconstruction.ply` plus `scan_alignment.mlp` as required inputs and uses a default 0.01 m voxel size. The official program can therefore be run later on a frozen output without downloading an occlusion archive; record its version and output separately. Even then, **four 1024-pixel views versus the benchmark's original full-resolution scene input** is a different experiment, and its whole-scene completeness denominator does not represent four-view visibility. Do not describe that result as a leaderboard-equivalent comparison.

The [occlusion archive](https://www.eth3d.net/documentation) contains a mesh, splats and image masks used for visibility-aware rendering. The released depth maps are aligned with the **original distorted** DSLR images, not these undistorted JPEGs. There is no need to download either for this first proximity run. If a later pixel-level visible-reference denominator is required, inspect the occlusion archive's HTTP size before acquiring it and implement the documented mesh/splat, depth-edge and mask rules with the correct distortion or a validated remap. Freeze that new evaluation population separately. Until visibility is implemented and validated, keep four-view completeness and physically verified surface accuracy **unclaimed**.
