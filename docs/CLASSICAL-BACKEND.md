# COLMAP → OpenMVS CPU experiment

This is an image-only research CLI for unknown camera poses. It estimates sparse cameras and points with PyCOLMAP 3.11.1, exports undistorted COLMAP images, then runs OpenMVS import, densification, mesh reconstruction, refinement and texturing. No supplied scan, depth, reference pose or fitted scale enters reconstruction. The output gauge is arbitrary. This experiment does not replace the app's `reconstruct` command.

## Pinned local toolchain

The existing `.local-tools/colmap-sparse/venv` supplies PyCOLMAP 3.11.1. The OpenMVS tools come from the upstream [v2.4.0 macOS arm64 release](https://github.com/cdcseacave/openMVS/releases/tag/v2.4.0), asset `OpenMVS_macOS_arm64.zip`, SHA-256 `3d4c616c97031b1ab6e2eecb0ddd5614fb99513c0782a32c9350602faf38799b`. The archive is 68,347,008 bytes; five selected CLI executables are extracted to `.local-tools/classical-backend/bin`. The [fetch helper](../scripts/classical_backend/fetch_openmvs.py) verifies the exact archive size/hash and extracts only those five members, keeping the 10 GiB free-space reserve. Each executable's SHA-256 is recorded in `result.json`. The native `InterfaceCOLMAP --help` starts on this M1 and `otool -L` shows macOS system libraries only. No global packages were installed. A local source build was not attempted because OpenCV, Eigen, CGAL and Ceres development packages are absent; the release binary is the bounded experiment toolchain.

OpenMVS identifies its project as [AGPL-3.0](https://github.com/cdcseacave/openMVS/blob/v2.4.0/LICENSE). It is a commercial desktop/server integration candidate under the approved AGPL roadmap, but this experiment is not release approval. App Store distribution is a separate question. `otool -L` shows dynamic links only; statically linked components and exact packaged dependencies still need review.

## Run

From the repository root, after placing the pinned binaries as above:

```sh
TMPDIR="$PWD/.local-tools/tmp" .local-tools/colmap-sparse/venv/bin/python -m scripts.classical_backend.fetch_openmvs
TMPDIR="$PWD/.local-tools/tmp" .local-tools/colmap-sparse/venv/bin/python -m unittest scripts.classical_backend.test_run -v
TMPDIR="$PWD/.local-tools/tmp" .local-tools/colmap-sparse/venv/bin/python -m scripts.classical_backend.run \
  --images .local-tools/test-data/ycb-cracker-box/photos \
  --output build-opencv/classical-ycb-001 \
  --max-views 60 --max-image-size 1600 --max-threads 2 \
  --max-gib 2 --timeout-minutes 30
```

The output must be fresh. The runner copies and hashes selected photos, caps total run time, logs, output bytes and sampled child RSS, and stops a stage when free disk approaches 10 GiB. `--image-list` accepts one basename per line. Every stage gets a log and a structured result; a nonzero exit or missing geometry marks the run failed. It requires at least three cameras and points from SfM, at least 70% photo registration by default, nonempty dense points and mesh faces validated through the full PLY payload, and a textured OBJ with valid face indices and nonempty texture assets. These checks establish artifact presence, not shape accuracy. The final `result.json` always marks `shipping_approved`, `metric_scale_verified` and `quality_accepted` false.

For a controlled shared-SfM experiment, `--sparse-model PATH` takes a binary COLMAP model from an independently recorded run. Add `--sparse-provenance`, `--sparse-manifest` and `--sparse-result` to verify the object-motion producer's photo and photo-derived mask hashes, exact options, and sealed binary model hashes. The runner checks registered photo names, copies and hashes the original photos, and records producer file hashes. Without those producer files it labels the model `external_unverified_model`, so no image-only provenance claim follows. It distinguishes raw from photo-mask SfM. This skips internal feature extraction, matching and mapping and does not demonstrate a single-invocation photo-to-mesh run.

The selected OpenMVS CLI sequence follows its [COLMAP import instructions](https://github.com/cdcseacave/openMVS/blob/v2.4.0/docs/wiki/Usage.md): `InterfaceCOLMAP`, `DensifyPointCloud`, `ReconstructMesh`, `RefineMesh`, `TextureMesh`. CPU execution is restricted to two native threads; PyCOLMAP feature extraction and matching also use CPU. By default, internal SfM uses one unknown shared `SIMPLE_RADIAL` camera, exhaustive matching and seed 0. `--max-image-size` limits undistorted images and densification uses resolution level 2 to keep the local trial bounded. The shared YCB model's producer used different documented SfM options, so the two modes must be reported separately.

The current standalone CLI can also reproduce the *settings* of the foreground producer without hardcoding the mask detector: `--pose-mask-dir` copies and hashes one `IMAGE_NAME.png` file per photo; `--matching sequential --sequential-overlap 8 --sift-max-features 1800 --sift-max-image-size 1200 --seed 20260927` select the bounded SfM configuration. Masks must be prepared independently from photos. `--sfm-max-models 5 --sfm-min-model-size 10` is now the generic mapper retry policy, allowing another candidate after a weak two-view start; the selected reconstruction is the largest returned by PyCOLMAP and is explicitly written to `sparse/0`. `--init-image-pair IMAGE1 IMAGE2` is an optional *manual-assisted diagnostic* by image names, never an inferred general fix. `--stop-after-sfm` records a sparse-only result and does not claim a completed backend. This option does not accept scan geometry or supplied camera poses. Native handoffs explicitly pass `dense.ply` to `ReconstructMesh`, `mesh.ply` to `RefineMesh`, and `refined.ply` to `TextureMesh`; the `.mvs` interface scene alone retains the original sparse points.

## M1 YCB observations (2026-09-27)

The independent [object-motion raw and foreground SfM reports](OBJECT-MOTION.md) used 60 real YCB cracker-box photos. The raw arm registered only 2 cameras. A photo-derived coarse pose-mask arm registered all 60 and produced 3,939 sparse points; the separately sealed producer report binds photo, mask and binary-model hashes. The shared-model OpenMVS run and its continuations are recorded as separate immutable results:

| Result | Actual stage outcome |
| --- | --- |
| `build-opencv/classical-ycb-foreground-001/result.json` | Adapter provenance variable-shadowing failure before native stages. |
| `build-opencv/classical-ycb-foreground-002/result.json` | 60 images undistorted and imported; native depth estimation completed 60 base maps and 45/60 maps in its second geometric pass, then a transient-file race in the runner's disk monitor stopped it. |
| `build-opencv/classical-ycb-foreground-003-continuation/result.json` | Copied the complete base depth-map cache; OpenMVS fused 60 maps in 7.9 s with `--geometric-iters 0` to a 56,684-point dense cloud. Native densification succeeded; the then-current validator rejected OpenMVS list properties in its PLY. |
| `build-opencv/classical-ycb-foreground-004-finish/result.json` | Reimported the same 60 cameras and explicitly passed that dense PLY to the native mesh tools. Rough mesh: 22,320 vertices / 44,561 faces. Refined and textured OBJ: 3,359 vertices / 6,612 faces, one 1024-pixel JPG atlas. Result `complete`; output 61.2 MB; free disk 20.58 GB. |
| `build-opencv/classical-ycb-foreground-005-e2e/result.json` | Fresh one-command masked run copied all 60 photos/masks but registered only 2 cameras / 357 points and stopped at the 3-camera gate before dense processing. Its features/descriptors match the producer byte-for-byte by image name, but matching differs slightly and automatic SfM chose NP3_192/198 as its initial pair, rather than the producer's NP3_192/162. |
| `build-opencv/classical-ycb-foreground-006-filtered/result.json` | Photo-mask point-support filter retained 34,172 of the same 56,684 native dense points at a frozen 48/60 camera threshold. With the same cameras and native mesh/refine/texture settings, the filtered run completed a 2,225-vertex / 4,404-face textured OBJ. It is a separate composed continuation. |

The successful textured artifact is a **composed continuation**, not a fresh one-command photo-to-mesh success or a single elapsed-time measurement. `004` took 0.51 s for reimport, 3.57 s for meshing, 92.05 s for refinement and 6.18 s for texturing; its largest sampled single-child RSS was 780 MB. The dense run spent roughly 10 minutes estimating depths before the runner race; `003` then fused cached maps in 7.9 s. The final geometry has no exact-zero-area triangles under full payload validation. Independent whole-mesh reference-fitted shape F1 at 1% of scan diagonal was **12.77%**; the visible mesh contains substantial board/background. This rejects object-quality acceptance. The fitted alignment cannot establish physical scale.

`003` and `004` are kept separate from the failed sources; the continuation runners log source hashes, stage commands, limits and native artifacts. OpenMVS's [usage guide](https://github.com/cdcseacave/openMVS/blob/v2.4.0/docs/wiki/Usage.md) documents reusing available depth maps for fusion. The completed 60 base maps were copied while partial geometric maps were omitted. `003` was thus a cached-depth diagnostic with geometric consistency disabled, and `004` used only its verified dense PLY plus freshly imported cameras. These choices are part of the result and cannot be silently presented as the original default dense run.

The [point-support filter](../scripts/object_motion/filter_cloud.py) is predeclared in the object-motion experiment and uses only the foreground SfM cameras and photo-derived coarse masks. Its output preserves every retained OpenMVS point record, including view lists and weights, byte-for-byte. `006` verifies the filter report's source dense-cloud, model, photo, mask and output hashes before calling `ReconstructMesh -p` on the filtered cloud. A repeated filter run produced the identical native PLY hash. No independent reference geometry entered this filter or either mesh run. Independent reference-fitted scoring improved F1 at 1% of scan diagonal from **12.77%** for `004` to **38.15%** for `006` (precision 42.63%, recall 34.52%). At 0.5% and 2%, filtered F1 was 19.48% and 63.54%. This is a substantial cleanup of background geometry but still rejects object-quality acceptance: important object surfaces are missing or distorted, and fitted alignment does not establish metric scale.

## Direct native-mask and mapper-replay controls

The pinned [OpenMVS v2.4.0 densifier](https://github.com/cdcseacave/openMVS/blob/v2.4.0/apps/DensifyPointCloud/DensifyPointCloud.cpp) supports `--mask-path` and `--ignore-mask-label 0`. It looks up `IMAGE.mask.png` by the image **stem** (for `NP3_000.jpg`, `NP3_000.mask.png`). The first attempted masked native run (`build-opencv/classical-ycb-native-masked-007`) is preserved as a failed filename-convention control: it supplied `NP3_000.jpg.mask.png`, which the native binary rejected. The [mask preparer](../scripts/classical_backend/dense_masks.py) now follows [COLMAP 3.11.1's pixel-center warp and rescale](https://github.com/colmap/colmap/blob/3.11.1/src/colmap/image/warp.cc), verifies unchanged poses and camera/model/image/mask hashes, and writes one native mask per undistorted image. Earlier mask directories `classical-ycb-dense-masks-001` and `-002` are obsolete diagnostics; `-003` is the canonical corrected 60-view set. These masks are photo-derived coarse pose support, **not** exact silhouettes or reference geometry.

`build-opencv/classical-ycb-native-masked-008/result.json` is a fixed-camera **composed-stage** experiment using the same 60 verified foreground sparse cameras and COLMAP-undistorted images as `002`; only native depth estimation receives the undistorted masks. At resolution level 2 (641×512 depth), OpenMVS completed densification in 56.97 s with 40,894 points, mesh reconstruction in 2.60 s with 38,902 rough faces, refinement in 122.47 s to 2,842 vertices / 5,680 faces, and texturing in 6.27 s. Output was 454 MB with 19.27 GB free afterward. This is not a fresh photo-to-mesh timing. Its source models, images, masks and binaries are hash-checked before/after; all native stage artifacts passed validators.

The [DMAP payload verifier](../scripts/classical_backend/verify_dmap_masks.py) reads v2.4.0's documented [raw depth header](https://github.com/cdcseacave/openMVS/blob/v2.4.0/libs/MVS/Interface.h) and compares *actual positive depth pixels* against nearest-resized masks. Across all 60 views in `build-opencv/classical-ycb-native-mask-effect-008.json`, the native masked maps have **701,110 positive pixels inside masks and zero outside**; the original unmasked `002` maps have 701,256 inside and 16,261,310 outside the same masks. This proves the native depth stage honored label 0, rather than merely accepting the mask CLI options. It is a support-mask effect measurement, not shape-quality acceptance.

Historical handoff caveat: the YCB masked arms passed the imported `scene.mvs`
plus an explicit dense point cloud/mesh into downstream stages, whereas the
baseline runner uses `dense.mvs`. Camera matrices match, but equality of all
derived scene metadata is not established; masks are not proven to be the only
downstream difference. Runs `008` and `011` share that historical handoff. The
later bunny mask arm explicitly uses `dense.mvs` to match its unmasked baseline;
the corrected helper does not retroactively change earlier native commands.

Independent reference-fitted surface scoring of `008` found F1@1% scan diagonal **42.04%** (precision 46.48%, recall 38.38%). Reusing `006`'s fitted transform unchanged in the exact shared sparse-camera gauge gives **35.49%** (precision 32.32%, recall 39.36%). The independently fitted `008` transform differs by about 41.8° rotation from `006`'s, so the independently fitted values cannot be read as a clean same-transform improvement over `006` (38.15%). Both are diagnostic fits to the separate reference scan after reconstruction; neither supplies metric scale or passes object-quality acceptance. This repeatedly inspected development object is not a held-out acceptance dataset.

For mapper diagnosis, `build-opencv/classical-ycb-sfm-probe-001/auto-retry` reused the `005` feature/match database with a generic five-model retry and still produced only a 2-camera model. The first automatic pair was NP3_192/198; later attempts also failed. `build-opencv/classical-ycb-sfm-pair-probe-002/manual-pair/result.json` copied that database first, then selected the independently successful producer's NP3_192/162 pair *by name*: it registered 60/60 and 3,934 points in 44.5 s, with unchanged source database/photo bytes. This isolates initial-pair sensitivity in the cached-DB replay. It does **not** establish that the generic pipeline always finds that pair, nor does it imply that the original `005` automatically recovered. The diagnostic `sfm_probe` may change SQLite file bytes when mapping directly, so subsequent probes copy the database first; no producer photo/model evidence was changed.

`build-opencv/classical-ycb-sfm-aligned-010/result.json` is the bounded *fresh* photo/mask→SfM-only replay with the same producer feature/matching options and explicit NP3_192/162 initial pair. Its separate feature, match and mapper processes registered 60/60 cameras and 3,928 points (107.04 s / 16.12 s / 18.08 s respectively), with no original photo or mask hash change. It stops deliberately before undistortion/native stages and records `sparse_complete`, so this result resolves the process-boundary concern for the assisted pair but is **not** a complete photo-to-mesh run. The small 3,939→3,928 point difference versus the producer likely reflects match/mapper numerical variability; that is an inference, not a proven sole cause.

The predeclared full-resolution native mask arm `build-opencv/classical-ycb-native-masked-009/result.json` used the same cameras, masks, geometric iterations, tower mode and native threads as `008`, changing only depth `--resolution-level` from 2 to 0. It completed the initial 60 depth maps but reached its frozen 2 GiB output cap during geometric consistency at 194.15 s (2,155,566,294 bytes), and the runner stopped the process. Free disk remained 16.96 GB; peak sampled child RSS was 765 MB. This is a preserved *failed* resource-bound result, not a full-resolution mesh comparison. No larger-cap or altered-geometric rerun is inferred from it.

`build-opencv/classical-ycb-native-masked-011-continuation/result.json` is a separately approved **cached continuation** of `009` under a 3 GiB cap, 10-minute native deadline and 10 GiB disk reserve. The [continuation helper](../scripts/classical_backend/resume_masked.py) verified all 60 complete full-resolution base DMAPs at 1282×1024 with positive depth only inside the photo-derived masks, copied their exact hashes and the same camera/image/mask inputs to a fresh directory, and excluded 20 partial geometric maps. The native log starts directly at geometric-consistent estimation, completes both requested 60-view passes, and fuses **151,387 points** in 111.02 s. Meshing produced 70,846 rough faces in 7.85 s; refinement produced a 5,407-vertex / 10,810-face mesh in 101.71 s; texture export took 6.17 s. The output was 1.65 GB, 14.85 GB remained free, the largest sampled child RSS was 1.02 GB, and source hashes were unchanged. Its complete geometry is a real native artifact but **not** a fresh full-resolution photo-to-mesh elapsed time or an object-quality acceptance result. Reference shape scoring is separate and must not be fed back into reconstruction.

Independent scoring of `011` reports F1@1% scan diagonal **42.06%** under its own fitted transform and **35.52%** under the fixed `006` transform in the common sparse-camera gauge. The full-resolution arm therefore did not establish object-quality acceptance or a clean same-transform gain over `008` (35.49%). These scores were computed only after the native output was frozen.

## Bunny same-input comparison

The independent 73-view bunny photo set is the same contrast-prepared image set used by the MVE control. A fresh automatic COLMAP attempt, `build-opencv/classical-bunny-contrast-001`, stopped with only 2/73 registered cameras. A separate mapper retry on its cached, image-only feature/match database returned a 73/73-camera, 3,133-point model; the returned in-memory model key did **not** match its on-disk directory index, so the verified good binary model is `build-opencv/classical-bunny-retry-002/probe/models/0`. This demonstrates that multiple-model retry can recover a strong model on this input, but is a composed diagnostic, not a fresh single-invocation success. The runner now selects the largest returned model and writes it explicitly to its own `sparse/0`; by default, model size is at least `min(10, selected view count)`.

The unmasked baseline `build-opencv/classical-bunny-retry-dense-002/result.json` imported that verified sparse model, completed native depth estimation with **344,487** points in 897.53 s and rough meshing with **266,899** faces, then reached its 20-minute global deadline during refinement. It remains failed evidence rather than being relabeled complete. The native rough mesh normalizes to `build-opencv/classical-bunny-retry-dense-002/rough-geometry.ply` with 133,484 vertices / 266,899 faces and no zero-area triangles. Neither that geometry conversion nor any reference scan enters reconstruction.

The first refine continuation, `build-opencv/classical-bunny-finish-003`, failed immediately because OpenMVS resolved scene image paths relative to its new working folder, where the images had not been copied. It is retained as failure evidence. The fresh `build-opencv/classical-bunny-finish-004/result.json` used the [bounded finish helper](../scripts/classical_backend/finish_rough.py) to copy/hash-check all 73 dense images, `dense.mvs` and `mesh.ply`, then completed refinement in **236.08 s** to **21,530 vertices / 42,919 faces** and texturing in **35.43 s** to a validated OBJ. The output was 122 MB, source hashes were unchanged and 14.64 GB remained free. Its geometry-only scorer export is `build-opencv/classical-bunny-finish-004/refined-geometry.ply` (same vertex/face counts, no zero-area triangles). This is explicitly a **composed continuation** of the rough mesh, not fresh photo-to-textured-mesh elapsed time; independent shape scoring follows separately.

The photo-only bunny masks are separately recorded in [BUNNY-MASKS.md](BUNNY-MASKS.md). `build-opencv/classical-bunny-dense-masks-001` warps all 73 original-coordinate masks into the verified undistorted cameras and checks image/model/mask hashes; the native `.mask.png` files are coarse object-support masks, not exact silhouettes. The distinct fixed-camera `build-opencv/classical-bunny-native-masked-005` arm uses the same resolution level 2, native default max resolution 2560, geometric iterations 2, tower mode 4 and 2 native threads as the unmasked baseline, adding native mask path and ignore-label 0. Its mesh/refine/texture steps consume `dense.mvs`, matching the baseline geometry-scene handoff. This remains a composed-stage comparison and does not claim fresh end-to-end elapsed time. The unmasked baseline and masked arm were run at different times, so wall-time differences are not a controlled speedup claim.

Native densification of `005` completed in **307.25 s** with **294,257 dense points**, versus 344,487 points in the unmasked baseline, and rough meshing completed in **18.57 s** with **252,486 faces**. Refinement took **262.46 s** and produced **20,690 vertices / 41,283 faces**; texturing took **35.52 s** and produced a validated OBJ and texture atlas. The full composed run is `complete`, output **806 MB**, free disk **13.88 GB**, source hashes unchanged. The geometry-only rough and refined scorer exports have no zero-area triangles; the refined export is `build-opencv/classical-bunny-native-masked-005/refined-geometry.ply`. These timings describe only the fixed-camera native arm, not earlier SfM or mask preparation.

The [DMAP payload verifier](../scripts/classical_backend/verify_dmap_masks.py) checked all 73 matched-size depth maps against the same native coarse masks: the unmasked baseline had **4,332,360 positive depths inside and 4,436,808 outside**; `005` had **4,332,340 inside and zero outside**. The frozen proof is `build-opencv/classical-bunny-native-mask-effect-005.json`. It establishes that masks affected native depth estimation, but says nothing by itself about surface accuracy; independent reference scoring is separate and does not enter reconstruction.

## Platform and result limits

Only the M1 release executables have been inspected. Linux and Windows have not been executed. A successful run would demonstrate a complete local CLI path, not textured object quality or metric scale. Reference surface scoring, if done, must use independent scan geometry only after reconstruction and must label any fitted similarity transform.
