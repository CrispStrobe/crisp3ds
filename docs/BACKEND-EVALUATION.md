# Reconstruction backend evaluation

This is a gate for R01–R04, not a complete-engine integration claim. The core now has optional OpenCV calibrated-pose and masked sparse-reconstruction stages; it has no dense-reconstruction backend. Selected native sources are recorded with exact pins and notice metadata. Release approval additionally requires review of actual shipped artifacts.

The user explicitly confirmed that the initial library suggestions are not constraints. MVE is not selected by default. Keep pose, track, depth and point-cloud contracts independent of its scene format.

| Candidate | Intended scope | Go/no-go evidence |
| --- | --- | --- |
| [OpenCV](https://github.com/opencv/opencv) | Still-image decoding, board poses, masked features and sparse triangulation implemented | 4.12.0 source archive pinned and selected CPU modules built on Apple Silicon; see [OPENCV.md](OPENCV.md). Rendered-image pose and sparse tests pass. Real-capture residual/scale validation and other target builds remain open. |
| [OpenMVG](https://github.com/openMVG/openMVG) + [Ceres](https://github.com/ceres-solver/ceres-solver) + [Eigen](https://gitlab.com/libeigen/eigen) | Optional sparse alignment and optimization if marker poses need refinement | Pin all versions and audit transitive code, including OpenMVG's vendored IJG JPEG license. Disable optional LGPL CXSparse and Ceres SuiteSparse; use Eigen sparse as portable baseline. Current Ceres requires Abseil, which also enters the inventory. Demonstrate that a known marker frame and object-only tracks keep metric scale and coordinate conventions. Do not import a general SfM pipeline solely to obtain a sparse bundle. |
| [MVE](https://github.com/simonfuhrmann/mve) selected `math`, `util`, `mve`, `dmrecon` | Dense depth from calibrated scene with real object-only sparse features | Pin and audit exact files; build selected libraries and tools on Apple Silicon, then Windows/Linux. Convert intrinsics, poses, tracks and masks without loss; confirm depth/normal quality, object isolation, runtime and memory on measured scans. If masks cannot control dense matching, adapt and validate selected code or reject this backend. |
| [PoissonRecon](https://github.com/mkazhdan/PoissonRecon) | Oriented cloud to surface | Pin/audit, then test normal orientation, mm units, thin LEGO geometry and bounded memory; require a measured real scan before adoption. |

MVE inspection on 2026-09-26 used upstream HEAD `bf2279f161ba962072ecac85224c15e82bc5f52e`. Its README calls the project maintenance mode and Windows support “sometimes.” The selected `math`, `util`, `mve`, and `dmrecon` static libraries compiled on Apple Silicon with the local compiler and libjpeg/libpng/libtiff development packages; this is only a compile spike, with no linked app or dataset test. Its root `make all` builds `apps/sceneupgrade`, whose source header says GPL-3; therefore that target fails this project's policy. `LICENSE.txt` flags `libs/sfm/sift.cc` and `libs/sfm/surf.cc` for separate algorithm/patent review. The selected dense target does not need those SfM files. `libs/dmrecon/dmrecon.cc` consumes bundle features for view selection and depth initialization, so camera matrices alone are insufficient. `libs/dmrecon/image_pyramid.cc` removes alpha from color input, and the inspected dense code has no mask path; alpha masks cannot be assumed to exclude board/background pixels. These observations create an R03 engineering gate, not a finding that a safe selected MVE package already exists.

The first full-stack go decision requires one calibrated, measured turntable dataset through the CLI: object masks, real sparse tracks, dense depths, oriented cloud, mesh, physical dimensions, repeatability, runtime and peak memory. Until then the CLI must report unavailable reconstruction capabilities honestly.

Follow-up execution: selected MVE now runs on the existing three-view rendered sparse fixture, with actual loaded-camera/seed checks rather than only a successful compilation. Agent and supervisor independently reproduced one 400×300 depth map. The known-plane radial-depth diagnostic has 94.20% object coverage and 3.10 mm matched MAE, but 36,927 valid depth pixels outside the object demonstrate the missing isolation gate. See [MVE-DENSE-SPIKE.md](MVE-DENSE-SPIKE.md). It remains a test-only candidate; this does not establish production masking, a complete scan, or acceptable photographed accuracy.

Primary build references: [OpenCV CMake options](https://docs.opencv.org/4.x/db/d05/tutorial_config_reference.html), [Ceres installation and sparse backends](https://ceres-solver.readthedocs.io/latest/installation.html), [MVE source and Makefiles](https://github.com/simonfuhrmann/mve/tree/bf2279f161ba962072ecac85224c15e82bc5f52e).

## Dense options to compare after pose estimation

| Approach | Fit to this application | Evaluation decision |
| --- | --- | --- |
| OpenCV calibrated pairwise stereo (`stereoRectify`, `StereoSGBM`, triangulation), then consistency filtering/fusion | Reuses the selected CPU library and known poses. Masks and image pairs remain under our control. Pair selection, invalid-disparity rejection, occlusion checks, normal estimation and fusion are application work. It is not a ready-made multi-view engine. | First small baseline experiment alongside MVE: test adjacent-angle object views, reject poor rectification/overlap, compare completeness and metric errors. Do not infer quality from library availability. |
| Selected MVE dense code | Existing multi-view implementation, but sparse seeds, mask integration and maintained builds remain substantial work. | Retain as a candidate. Compare measured output and engineering cost with the pairwise baseline before adoption. |
| AliceVision | Broader photogrammetry framework with MPL-2.0 principal license. Its documented dense-depth path involves CUDA, and its dependency graph is substantially larger than the proposed CPU baseline. | Not the first macOS CPU integration choice. Reconsider for a separate supported GPU target only after checking exact depth implementation and transitive licensing. |
| Open3D geometry/fusion | Useful downstream geometry APIs; its documented reconstruction system consumes RGB-D sequences. Ordinary photographs do not supply its required depth maps. | Consider for fusion/geometry if beneficial; not a direct replacement for photo-to-depth estimation. |

References checked 2026-09-26: [OpenCV StereoSGBM](https://docs.opencv.org/4.x/d2/d85/classcv_1_1StereoSGBM.html), [OpenCV calibrated geometry](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html), [AliceVision dependencies and CUDA options](https://github.com/alicevision/AliceVision/blob/develop/INSTALL.md), [AliceVision licensing](https://github.com/alicevision/AliceVision/blob/develop/COPYING.md), [Open3D reconstruction inputs](https://www.open3d.org/docs/latest/tutorial/ReconstructionSystem/index.html).

The initial rankings are engineering judgments based on documented scope and platform goals. A test-only OpenCV SGBM baseline has now run on the real Piano stereo fixture: 83.9% reference-pixel coverage and 31.3% error >2 px or missing at a locally derived 705×480 resolution. See [measured evidence, provenance and next tasks](DENSE-EVALUATION.md). This does not select a production backend; no dense engine has passed the measured-object gate yet. A silhouette/visual-hull fallback would be a different product mode and must disclose that it cannot recover concavities absent from silhouettes; do not silently present it as photogrammetric surface recovery.
