# msplat-ios source audit (not an execution result)

Audited 2026-09-27 at [`frs0n/msplat-ios` commit `e8611098583059b82e0b7d35259fb4e9c42df248`](https://github.com/frs0n/msplat-ios/tree/e8611098583059b82e0b7d35259fb4e9c42df248). This was a read-only inspection of small GitHub source files and the repository tree: no clone, build, device test, training run, or quality score. The comparison entry in [`pipeline-evidence.json`](../benchmarks/pipeline-evidence.json) is therefore **audited**, not executed.

## What exists

The [iOS example](https://github.com/frs0n/msplat-ios/blob/e8611098583059b82e0b7d35259fb4e9c42df248/examples/ios/README.md) imports a **pre-existing COLMAP reconstruction** (`cameras`, `images`, and optionally sparse points), trains, previews, and exports a Gaussian PLY. Its [session](https://github.com/frs0n/msplat-ios/blob/e8611098583059b82e0b7d35259fb4e9c42df248/examples/ios/MsplatExample/TrainingSession.swift) invokes `GaussianDataset` and repeated `GaussianTrainer.step()`; the [Swift trainer](https://github.com/frs0n/msplat-ios/blob/e8611098583059b82e0b7d35259fb4e9c42df248/swift/Sources/Msplat/GaussianTrainer.swift) exposes training, rendering, and export. [Metal kernels](https://github.com/frs0n/msplat-ios/blob/e8611098583059b82e0b7d35259fb4e9c42df248/core/metal/msplat_metal.metal) include forward and backward rasterization and optimizer work. It is **a trainer as well as a renderer**, not an RGB-to-pose or RGB-to-mesh pipeline. No camera capture, ARKit/LiDAR, or SfM stage is present in the inspected app; “no LiDAR” describes its input requirement, not demonstrated end-to-end RGB-only reconstruction. The PLY is Gaussian splats, not a watertight triangle mesh.

The [COLMAP loader](https://github.com/frs0n/msplat-ios/blob/e8611098583059b82e0b7d35259fb4e9c42df248/core/src/loaders/load_colmap.cpp) reads binary or text models, accepts several pinhole/radial/OpenCV camera models, sorts frames by filename, converts COLMAP world-to-camera poses to OpenGL camera-to-world, and initializes from sparse points. Its [input-data code](https://github.com/frs0n/msplat-ios/blob/e8611098583059b82e0b7d35259fb4e9c42df248/core/src/input_data.cpp) **re-centers and rescales** cameras and points. Any external geometric or sensor comparison must preserve and invert that transform. The same file's built-in `testEvery` split selects sorted indices divisible by `testEvery`; that is not automatically our predeclared held-out frame split. Build a train-only COLMAP package and keep held-out photos out of the loader, rather than relying on a later evaluation flag. The example has no reviewed object-mask input path; any background suppression or mask support needs source-level validation before claiming an object-only model.

## Rotating-object pose boundary

A stationary camera viewing a rotating object is **not** the static-world camera trajectory assumed by the COLMAP loader. A valid object-centric package needs per-frame *virtual* camera poses relative to one fixed object frame, with intrinsics and sparse seeds in that same frame. Our image-estimated YCB camera lane is a plausible input to test, but this audit did not feed it into msplat. Supplied turntable angles or supplied Berkeley poses would create a separate supplied-camera lane, not an image-only result. In either lane, keep held-out photos and scanner reference geometry out of pose estimation and training, and bind each model, image list, camera convention, split, and output by hash. Failure to model rotating background/lighting remains a risk even with virtual poses.

## Platform, evidence, and license limits

The [README](https://github.com/frs0n/msplat-ios/blob/e8611098583059b82e0b7d35259fb4e9c42df248/README.md) reports an iPhone **15 Pro** overflow case and seven nondeterministic garden runs; it says the upstream M4 Max benchmarks were **not re-run by the fork**. It gives no iPhone **13 mini** training result, memory limit, quality measure, or completion evidence. The [Swift package](https://github.com/frs0n/msplat-ios/blob/e8611098583059b82e0b7d35259fb4e9c42df248/swift/Package.swift) targets iOS 18 and macOS 15; the [build script](https://github.com/frs0n/msplat-ios/blob/e8611098583059b82e0b7d35259fb4e9c42df248/scripts/build-xcframework.sh) creates the missing XCFramework and platform-specific metallibs. A platform target is not validation on an iPhone 13 mini or M1 Mac. The [upstream `rayanht/msplat` README at `6b819711fa7c90f054567cb4fb4937743367afdd`](https://github.com/rayanht/msplat/blob/6b819711fa7c90f054567cb4fb4937743367afdd/README.md) describes Apple-Silicon Metal training, but its reported performance is on **M4 Max**, not M1; it is context, not a transferred benchmark.

The fork's [LICENSE](https://github.com/frs0n/msplat-ios/blob/e8611098583059b82e0b7d35259fb4e9c42df248/LICENSE) is Apache-2.0 with upstream copyright retained. The audited recursive tree contains **no Git submodule entries**. The Metal kernel is a tracked source file in this fork, not an external binary; its own header has no separate license notice. However, [CMake](https://github.com/frs0n/msplat-ios/blob/e8611098583059b82e0b7d35259fb4e9c42df248/CMakeLists.txt) fetches `nlohmann_json` v3.11.3, `nanoflann` v1.5.5, and CLI11 v2.4.2 by tag archives. Their separate notices and exact downloaded archive hashes should be recorded before redistribution, as should the upstream/fork notices and any packaged metallib/XCFramework; this is a provenance/compliance checkpoint, not legal clearance.

## Actionable next experiment, without a quality claim

On an available M1 Mac, first test **build and one bounded train-only object package** using a reviewed image-estimated COLMAP model, explicit image whitelist, and sparse points. Verify camera projections before training; save the loader's center/scale and invert them for exports; use fixed iterations/downscale/cache cap and capture peak resident memory, wall time, output hash, and held-out renders. Then score rendering only on the previously frozen held-out images. An iPhone 13 mini trial is a distinct feasibility experiment with device OS, thermal state, memory headroom, training completion, and output logged; neither the source nor this audit predicts success. Surface accuracy would still need a separately validated splat-to-mesh route and independent geometry evaluation. No M1, iPhone, render, or mesh result is registered here.
