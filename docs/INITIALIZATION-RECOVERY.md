# Image-only YCB initialization recovery trials

These are bounded **cached-feature mapper** experiments, not fresh image-to-mesh pipelines or general reconstruction improvements. They use the same 60 foreground-support-extracted cracker-box photos, source feature/descriptor/raw-match/verified-geometry database, and no supplied camera intrinsics, poses, depth, or reference mesh. The image-derived masks were used when the source features were originally extracted; no segmentation is newly inferred here.

## One predeclared seed trial: failed

The read-only [initialization diagnostic](INITIALIZATION-DIAGNOSTIC.md) preselected `NP3_018.jpg` / `NP3_030.jpg` (#4/#6) using source-database inliers and exact third-image feature cycles only. The first two fresh output folders, `initialization-recovery-001` and `-002`, failed **before** SfM: the first exposed a pinned PyCOLMAP list-vs-dict API mistake, and the second correctly stopped on newly observed SQLite WAL/SHM sidecars. They are retained with logs/status, not counted as mapping outcomes. The one actual [mapper report](../build-opencv/object-motion/initialization-recovery-003/cached_seed_trial/report.json) (SHA-256 `87343ede7c175af9f70f9043553edced631eeb7076546777d99fe0b17c82fa8a`) used the frozen seed, two native threads, 180-second bound, 100-MiB output cap, and 10-GiB free-space floor. It copied the cached database but ran no feature extraction, descriptor matching, or two-view re-verification. The original image-only `SIMPLE_RADIAL` camera began at the source DB values `f=1536`, `cx=640`, `cy=512`, `k=0`, with mapper intrinsic refinement enabled as in the earlier image-only arm.

The result is **failure**, not a successful fix: 2/60 cameras and 359 sparse points after 0.273 s of mapping, with final `f=9950.99 px`, `k=−228.714`. It rejected all ten distinct attempted third images twice; the closest candidates saw up to 290 seed points, so low correspondence count alone does not explain rejection. Both predeclared gates failed: at least three cameras, and a conservative finite `SIMPLE_RADIAL` check (`640≤f≤1920 px`, `|k|≤0.5`, principal point inside the 1280×1024 image). Registration itself would not have been a mesh-quality proof. There was no seed sweep or tuning against Berkeley/Google metadata.

## Accidental source-DB byte change and explicit rebind

While adding a pinned-API test, this agent inadvertently opened the original `build-opencv/object-motion/foreground/database.db` with writable `pycolmap.Database.open`. Its **file bytes changed** from historical SHA-256 `a36cc364bf9b7d7a8357c12ee3619002dd2c85696f09b5921d1f9e926f2e3ca7` to `5850e6c508df3b296169a25334abdbae2f5f7cdfc3628a78d7fd21717e457562`; the original was **not restored or overwritten**. A first pre-mapper copy also changed bytes when opened through the same API. No byte-identical historical copy was found among the local databases. This was an implementation error, not a planned processing step.

Before any native mapper call, the separate [mutation audit](../build-opencv/object-motion/initialization-recovery-cache-audit-002/report.json) (SHA-256 `14116ca9768a40d5f3265cbd22b14a7043f216be8f3f671e2bdbba1caacc0db5`) pinned the **new** source bytes and checked SQLite integrity, schema and all six logical tables against the retained first copy. Keypoints, descriptors, raw matches, and two-view-geometry table digests also match earlier recorded pre-mutation values; the camera row remains `SIMPLE_RADIAL,1280×1024,[1536,640,512,0],prior=0`, and the 60 photo hashes/producer provenance/model hashes still verify. Historical *full* camera/images table digests were not saved before the mistake, so byte-identical or complete pre/post logical identity is **not proven**. The audit explicitly records that unknown. The source's subsequent WAL was zero bytes and SHM 32 KiB; reads now use immutable read-only SQLite, and the mapper refuses to copy a source with nonempty WAL. The `003` copied database changed bytes during native access but all six logical table digests/schema remained equal before and after. This trial is an **explicitly rebound-cache experiment**, never an exact historical-byte replay. Future consumers must use its new hashes and keep that limitation visible.

The `003` sparse model files and copied-cache before/after hashes are individually sealed in its report. No final mesh was made from this failed sparse model.

## Separate exploratory fix: freeze initialization, then refine after 60 views

The observed `003` focal/distortion runaway motivated a **new, explicitly exploratory** arm with the *same* cached logical tables and seed—not a post-score seed retry. In [004's sealed producer report](../build-opencv/object-motion/initialization-recovery-004-fixed-intrinsics/cached_seed_trial/report.json) (SHA-256 `9a7ddeac8b99ab3ec41a512aec0b852b555aa6176860d2047460e3f87f910b63`), global/local bundle adjustment focal, principal-point, and extra-parameter refinement, plus absolute-pose focal/extra refinement, were all disabled during mapping. All other mapper settings, frozen seed, source-image hashes, and rebound-cache provenance remained the same. The starting `SIMPLE_RADIAL` `[1536,640,512,0]` is an **image-only database heuristic**, not supplied Berkeley calibration. A pinned PyCOLMAP options-contract test checks every exposed intrinsic-refinement toggle. One 180-second/100-MiB/two-thread bounded run then registered **60/60 cameras and 3,921 sparse points** in 10.15 s; the final camera exactly retained `[1536,640,512,0]`. The copied cache's six logical tables were unchanged. This establishes sparse *feasibility* for this one case, not camera truth or surface quality: `f=1536` is materially different from the independent Berkeley fx≈1081 and prior image-only free-intrinsics estimates near 1080.

The next approved **two-phase** check did not remap or recompute features. It verified all three binary hashes of `004`, copied that 60-view model to fresh output, and ran one pinned PyCOLMAP CPU global bundle adjustment with focal/extra parameters and extrinsics enabled, principal point fixed, two threads, at most 50 solver iterations/50 solver seconds, and a 60-second outer/100-MiB cap. The [005 refinement report](../build-opencv/object-motion/initialization-recovery-005-delayed-refinement/ba_trial/report.json) (SHA-256 `80241c6c8d72097ce38a9a046aadfa495c1027bbfbd05a6a9480ad09b02c7e10`) seals both copied input and refined model binaries. All 60 cameras and 3,921 points remained; after 3.58 s of BA, image-only `SIMPLE_RADIAL` focal moved **1536→1103.95 px** and radial `k` **0→−0.05134**, with principal point exactly `(640,512)`. The same 24,358 *training* reprojection observations changed from median/p95 **0.3696/1.6029 px** to **0.3533/1.5834 px**. Counts, finite/plausible camera, fixed-principal, and finite-residual gates passed. The refined output is separate; `004` was not overwritten.

This is evidence for a practical engineering pattern on the cached cracker-box case: defer free-intrinsic self-calibration until a multiview model exists. It does **not** isolate which free parameter caused `003` failure, prove a general fix, validate the camera against held-out observations, or demonstrate mesh accuracy. In particular, both the seed policy and the 004→005 refinement were selected during development using this one object; subsequent quality estimates would need independent evaluation and must retain the source-DB rebind disclosure. No additional variants were run.
