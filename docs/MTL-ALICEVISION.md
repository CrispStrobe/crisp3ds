# Metal AliceVision fork: bounded source audit

Status (2026-09-27): **audited, not built or run**. The immutable audit revision is [`505197b6fc13e016718c12bc2731d3862593f611`](https://github.com/philippremy/MTL-AliceVision/tree/505197b6fc13e016718c12bc2731d3862593f611), the then-current `main`/HEAD. No AliceVision sources, packages, or dependencies were downloaded into this workspace. A separate four-value Metal compute smoke passed on the Apple M1; this is **not** an AliceVision test.

The fork [calls itself a proof of concept](https://raw.githubusercontent.com/philippremy/MTL-AliceVision/505197b6fc13e016718c12bc2731d3862593f611/README.md), with a working Metal backend but a bundle incompatible with upstream Meshroom because of hardcoded paths. Its depth-map [CMake target compiles five `.metal` shader sources and embeds a shader library](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/Sources/Libraries/AVDepthMap/CMakeLists.txt); the [pipeline CMake](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/Sources/Binaries/Pipeline/CMakeLists.txt) exposes depth estimation/filtering when Metal is enabled, plus meshing, mesh filtering, and texturing. This is a distinct native-Metal branch, **not** evidence that current upstream AliceVision is CUDA-only. Upstream [merged a SYCL MVS port in PR 2077](https://github.com/alicevision/AliceVision/pull/2077) and its [pinned `depthMap_sycl` target](https://github.com/alicevision/AliceVision/blob/8e4f0be76b250f0dd04b11d2a9a457d59d71b42c/src/aliceVision/depthMap_sycl/CMakeLists.txt) offers a separate path. But the fork author [reports `double`/fp64 kernel compilation blockers for AdaptiveCpp's experimental Metal backend](https://github.com/orgs/alicevision/discussions/2160); upstream SYCL on CPU is a different candidate from SYCL-on-Metal. The fork's [COPYING](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/COPYING.md) still says CUDA is required for depth; that inherited sentence is stale relative to these build targets. Neither path has been benchmarked here.

## Exact adapter seam, if a build later succeeds

Use AliceVision `SfMData` as the camera/scene contract, **not** a COLMAP model path or OpenMVS `.mvs`. The fork's [`aliceVision_depthMapEstimation`](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/Sources/Binaries/Pipeline/main_depthMapEstimation.cpp) requires `--input <sfmData> --imagesFolder <images-by-view-UID> --output <raw-depth-dir>`; relevant bounded controls include `--downscale`, `--rangeStart`, `--rangeSize`, `--nbGPUs`, and tile/camera settings. Then [`aliceVision_depthMapFiltering`](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/Sources/Binaries/Pipeline/main_depthMapFiltering.cpp) requires `--input <same-sfmData> --depthMapsFolder <raw-depth-dir> --output <filtered-dir>`. [`aliceVision_meshing`](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/Sources/Binaries/Pipeline/main_meshing.cpp) requires `--input <sfmData> --output <dense-sfmData> --outputMesh <mesh>` and `--depthMapsFolder <filtered-dir>` for depth-based meshing. [`aliceVision_meshFiltering`](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/Sources/Binaries/Pipeline/main_meshFiltering.cpp) takes `--inputMesh/--outputMesh`; [`aliceVision_texturing`](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/Sources/Binaries/Pipeline/main_texturing.cpp) takes `--input <dense-sfmData> --inputMesh <filtered-mesh> --output <texture-dir>` and optionally `--imagesFolder`. This is a source-derived proposed chain, not a verified execution. A future adapter must first produce/validate SfMData and UID-named photos, bind input hashes, and validate depth/mesh/texture payloads before labeling any stage successful.

No `mask` option occurs in the fork's depth-estimation CLI source; object-mask support cannot be assumed from our OpenMVS adapter. Its [Metal branch logs command-buffer errors and then calls `std::_Exit(EXIT_SUCCESS)`](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/Sources/Binaries/Pipeline/main_depthMapEstimation.cpp#L460-L505) to bypass a documented autorelease-pool crash. Therefore **exit code zero is insufficient evidence** of complete/valid depth maps. A full adapter would have to check per-view outputs and error logs; the forced exit also merits upstream investigation before shipping.

## Build, dependencies, and licensing

The [top-level CMake](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/CMakeLists.txt) requires CMake ≥3.28/C++20, defaults macOS to a **universal arm64+x86_64** build, and defaults tests, GUI/Qt plugins, GUI, ONNX, OpenCV, and numerous other optional features on. A bounded Apple-Silicon-only CLI attempt would need explicit feature pruning and `CMAKE_OSX_ARCHITECTURES=arm64`, without claiming that combination has been validated. The [dependency handler](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/CMake/HandleDependency.cmake) automatically builds missing required packages from source; merely configuring the project is **not** a safe no-download preflight. Boost, Ceres, OpenImageIO, OpenEXR, Geogram, Assimp, SuiteSparse, and others appear in the [required dependency list](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/Sources/CMakeLists.txt). The same file sets `ALICEVISION_HAVE_METAL=1` after warning that no Metal compiler was found, a configuration risk. These need a constrained dependency inventory/patch or isolated build environment before any build authorization.

GitHub's [releases API](https://api.github.com/repos/philippremy/MTL-AliceVision/releases) and [tags API](https://api.github.com/repos/philippremy/MTL-AliceVision/tags) returned empty lists at audit time. The [recursive tree](https://api.github.com/repos/philippremy/MTL-AliceVision/git/trees/505197b6fc13e016718c12bc2731d3862593f611?recursive=1) had no gitlink/submodule entries; this does **not** pin dependencies built by CMake. Metal-cpp is vendored under [Apache-2.0](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/ThirdParty/metal-cpp/LICENSE.txt), the vendored CMake-Metal helper has a [BSD-style license](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/CMake/ThirdParty/CMake-Metal/LICENCE.txt), and [COPYING](https://github.com/philippremy/MTL-AliceVision/blob/505197b6fc13e016718c12bc2731d3862593f611/COPYING.md) identifies core AliceVision MPL-2.0 plus other notices. Desktop/server integration may be explored under the project's license review; neither shipping all dependencies nor App Store distribution is approved by this audit.

## Local preflight and decision

Do not assume the latest prebuilt AliceVision release includes SYCL. At this
check, upstream's [latest release](https://github.com/alicevision/AliceVision/releases/tag/v3.3.0)
was `v3.3.0`, published 2025-08-19, before PR #2077 merged. Its tag has no
`src/aliceVision/depthMap_sycl/CMakeLists.txt`. The Linux/Windows release assets
are about 1.5 GB each; they were not downloaded. Evaluate a pinned post-merge
source build for SYCL rather than relying on the latest-release name.

`python3 scripts/metal_backend/preflight.py` is read-only and reports unknown `build_ready` even when host tools exist. On this Apple M1 it found Xcode/SDK, `metal`, `metallib`, `clang++`, CMake 4.1.1, Ninja, and about 11.75 GiB free. `python3 scripts/metal_backend/smoke.py` compiled and ran a four-element Metal vector-add oracle, then removed its project-local scratch executable; it passed 4/4 values. Neither test compiled a fork shader or checked dependencies.

**Decision:** no fork build on this ~12 GiB-free host under the 10 GiB floor. GitHub reports ~9.7 MB of repository data, but full dependency downloads/build products are unbounded by that number. A build may be feasible in a separate, disk-quota-controlled environment after CMake dependency resolution is made non-downloading, feature flags and architecture are frozen, source/third-party licenses reviewed, and output validators are specified. Any local write over 100 MiB requires new approval. Prioritize evaluating current upstream SYCL/CPU separately; native Metal remains a research candidate, not an integrated backend.
