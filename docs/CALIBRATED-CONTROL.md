# Calibrated-intrinsics YCB native control

This is a separate **intrinsics-assisted** control, not an image-only reconstruction. The upstream `ycb_calibrated_intrinsics_sfm_v1` producer uses Berkeley NP3 RGB calibration for one fixed `FULL_OPENCV` camera. Its poses and sparse points are still estimated from the same 60 original RGB photos and cached photo features/matches; no supplied pose, depth map, object scan or reference mesh may enter mapping or the native stages. The producer must explicitly record the assumption that the Berkeley principal point is in OpenCV integer-centered pixels and was shifted by `+0.5` for COLMAP. The unshifted/shifted choice was frozen before object-mesh scoring; it is not to be selected by the held-out shape reference.

The [calibrated consumer](../scripts/classical_backend/calibrated_control.py) accepts only a complete producer report with the exact lane/schema, 12 finite `FULL_OPENCV` parameters, registered binary COLMAP model and point counts, exact hashes for all 60 original photos, the original photo-derived pose masks, the Berkeley calibration HDF5, and the three binary model files. It independently reads the HDF5 `/NP3_rgb_K` and `/NP3_rgb_d` datasets with `h5dump -m %.17g`, constructs the full 12 parameters with the predeclared `+0.5` principal-point shift and checks both the report and binary model against those values. It requires exactly 60 finite registered image poses, one shared 1280×1024 calibrated camera, finite sparse points and a matching photo set. It also requires the producer's unchanged cached-feature/raw-match hashes, reverified-geometry hash and recorded re-verification options. The latter are producer evidence; the consumer independently rehashes the files it actually reads (photos, masks, calibration and model), not an unavailable historical database snapshot. The output provenance label remains `oracle-assisted intrinsics; image-estimated poses` throughout.

The bounded chain copies and hashes the images/model into a fresh output, undistorts with PyCOLMAP 3.11.1 at max image size 1600, warps the **photo-derived** masks through the full rational Brown–Conrady model, imports the COLMAP workspace, then runs OpenMVS v2.4.0 CPU `DensifyPointCloud`, `ReconstructMesh`, `RefineMesh` and `TextureMesh`. The native dense profile requests resolution level 2, max resolution 1600, two geometric passes, tower mode 4, ignore mask label 0, and two threads. Mesh/refine/texture explicitly use `dense.mvs` and the appropriate PLY handoffs. A total ten-minute deadline, 1 GiB output cap, sampled-child memory/log limits and 10 GiB free-space floor apply; the preflight also reserves the batch's 1.5 GiB total-new-data allowance. Stage logs, exact commands, hashes, artifacts and failures remain in `result.json`. A complete artifact still has arbitrary scale and `quality_accepted: false` pending independent scoring.

Mask warping preserves COLMAP's `x+0.5` image-center convention and OpenCV's integer-index remap addressing (`−0.5` at the source sample). The `FULL_OPENCV` branch uses all `k1,k2,p1,p2,k3,k4,k5,k6` coefficients; dropping Berkeley's nonzero `k3` is rejected. Tests compare off-center projections and warped binary masks with independent `cv2.projectPoints`, including target-image rescaling. The generated `IMAGE.mask.png` files are coarse support masks, **not** silhouettes or supplied dataset masks.

The native depth-camera audit reads raw v2.4.0 DMAP headers. [OpenMVS's COLMAP importer](https://github.com/cdcseacave/openMVS/blob/v2.4.0/apps/InterfaceCOLMAP/InterfaceCOLMAP.cpp) subtracts 0.5 from COLMAP principal points; [OpenMVS camera resizing](https://github.com/cdcseacave/openMVS/blob/v2.4.0/libs/MVS/Camera.h) maps an integer-centered pixel coordinate `c` to `(c+0.5)·s−0.5`. Thus a COLMAP `PINHOLE` camera `(fx,fy,cx,cy)` at `W×H` has depth-map `K = (fx·sx, fy·sy, cx·sx−0.5, cy·sy−0.5)` for scales `sx=Wdepth/W`, `sy=Hdepth/H`. The [DMAP header](https://github.com/cdcseacave/openMVS/blob/v2.4.0/libs/MVS/Interface.h) stores K/R/C at its selected native image resolution, not necessarily the original undistorted image resolution. On all 60 prior YCB `008` maps, this exact formula gives maximum K difference **0 px**, R difference `7.8e−16`, and center difference `3.6e−15`; synthetic tests fail on a `+0.01 px` principal-point perturbation. The same all-view audit confirms **zero** native positive depth pixels outside the photo-derived ignore-label-0 masks. This proves camera-coordinate handoff and native mask application, not true camera poses or object shape.

For diagnosis, camera evidence (fixed calibration, feature/match provenance, SfM track reprojection and optional post-hoc comparison with supplied metadata) must be reported separately from depth/geometry evidence (native DMAP mask support, exact K/R/C handoff, cross-view depth reprojection and final projected surface support). Depth or photo agreement on the *input* views is a self-consistency check, not an independent shape oracle. The Google-scanner reference may be used only after reconstruction for descriptive surface scoring, never to select the camera arm or tune masks.

The sealed [serial producer report](../build-opencv/object-motion/calibration-ablation-002/calibrated_shifted/report.json) passed the strict input gate: **60/60** registered photos, **3,942** finite sparse points, exact original-photo/pose-mask/HDF5/model hashes, one fixed `FULL_OPENCV` camera and unchanged cached features/raw matches. The same serial re-verification method's image-only control registered only **2/60**, so it is not a paired image-only mesh-quality baseline. The earlier parallel-verifier calibrated attempt crashed before mapping; its failed artifact is preserved separately. Neither outcome is evidence that serial verification or calibrated intrinsics is generally reliable.

Root approved one native attempt in [calibrated `012`](../build-opencv/classical-ycb-calibrated-012/result.json). Its 60-image undistortion, full-model photo-mask warp and native COLMAP import passed. Densification stopped at the hard **1 GiB output cap** after **38/60 initial depth maps** and 47.4 s: sampled output was **1,098,876,607 bytes**, with >10 GiB free remaining. The first native DMAP was **1277×1015**, about 25.9 MB. There is no complete calibrated dense cloud, mesh, texture, depth-camera audit or surface score; `012` is a bounded failure, not a quality result. No retry or cache continuation was launched.

This exposed a pinned OpenMVS resolution boundary. [`TImage::computeMaxResolution`](https://github.com/cdcseacave/openMVS/blob/v2.4.0/libs/Common/Types.inl) right-shifts the longer image edge by the requested level, then decreases the level if the result is below `--min-resolution`; [densification calls that function](https://github.com/cdcseacave/openMVS/blob/v2.4.0/libs/MVS/SceneDensify.cpp) for every view. With its default minimum **640**, a 1277 px undistorted image falls from requested level 2 to **actual level 0** because 1277/2 truncates to 638, while 1280 and 1282 px fall to level 1 (640 and 641 px). Prior image-only masked `008` used **641×512** native DMAPs and completed with 40,894 dense points in 454 MB; the larger cached full-resolution `011` did not improve its fixed-gauge quality. These are controls, not predictions for calibrated geometry.

For future runs, the consumer now passes an explicit minimum **600** and computes the pinned effective resolution from each undistorted image *before* starting native dense work; the 1277 px case would become actual level 1 at 638 px. It rejects any unexpected full-resolution view and an estimated two-generation DMAP footprint exceeding the output cap. The estimate uses the observed 20-byte/pixel DMAP layout plus metadata/headroom and is **not a guarantee**; the runtime byte/free-space limits remain authoritative. This is a post-`012` safety change and has **not** been used to produce a calibrated mesh. If the producer fails the **60/60** gate in another run, the lane stops before undistortion or native dense processing.
